# `reviews/` — Reviewer Evidence Storage

**Purpose:** a dedicated, repository-level location for original
reviewer-supplied evidence (screenshots, downloaded source documents,
reviewer-captured artifacts) that feed the Chunk 7.39 intake
pipeline.

**Owner selected approach:** Chunk 7.31 §4.1 — Option A, a dedicated
`reviews/` directory (Chunk 7.41). Alternatives (PR comments,
appended governance docs) were evaluated in Chunk 7.31 and
documented as rejected or deferred.

**What this directory is not:**

- Not a replacement for `hybrid_dataset/raw/evidence_intake/`
  (which holds pipeline-generated **copies** created by
  `nlp_semantic.intake.ingest_evidence`).
- Not a dataset directory. Nothing here becomes an `Achievement`,
  `Annotation`, `Evidence`, or `SourceRegistry` row automatically.
- Not an approval mechanism. A file's presence here is not source
  approval, reviewer authentication, or annotation verification.
- Not a `reviews/manifests/` subdirectory. Intake-pipeline
  manifests already live under `hybrid_dataset/intake/manifests/`
  (Chunk 7.39). Creating a second manifest store would introduce
  the second evidence-management system Chunk 7.41 §2 explicitly
  forbids.

---

## 1. Directory layout

```
reviews/
├── README.md                   # this file (TRACKED)
└── evidence/
    └── .gitkeep                # structural marker (TRACKED)
    # ↑ evidence file contents stay LOCAL and are NOT committed
    #   by default (see §5 "Git tracking and privacy policy").
```

The layout is deliberately minimal — one subdirectory and one
`.gitkeep`. If more structure is later needed (per-source
subdirectories, per-year partitions), the owner adds it as a
small follow-up chunk; Chunk 7.41 does not pre-create empty
sub-trees.

## 2. What belongs in `reviews/evidence/`

**Belongs:**

- Reviewer-captured browser screenshots of a public source page
  (PNG, PDF export).
- Original source documents the reviewer downloaded (press
  releases, PDF reports, certificate images) with a stable
  reference to the source URL.
- Reviewer-authored YAML sidecar notes documenting capture
  context (one per evidence file, see §4).

**Does not belong:**

- Search-result screenshots that are not of the primary source
  page itself.
- AI-generated screenshots.
- Synthetic evidence created to populate the directory for
  demonstration or testing. (Tests use their own temporary
  fixtures per Chunk 7.39's `test_pipeline.py`.)
- Reconstructed documents (e.g. a rewrite of the source made
  from memory).
- Unverified web captures of a page whose identity the reviewer
  did not verify.
- Any `Achievement` record, `Annotation` row, or dataset-shaped
  artifact. Those live under `hybrid_dataset/`.
- Model-generated summaries presented as original evidence.
- Private student PII that is not already present in the source
  the reviewer captured. If the reviewer's capture incidentally
  includes PII (e.g. a reviewer's own browser bookmark bar), the
  reviewer must redact before saving.
- Credentials, API keys, `.env` files, or any secret.

## 3. Supported file types

Extensions the Chunk 7.39 intake pipeline (`SUPPORTED_EXTENSIONS`
in `src/nlp_semantic/intake/pipeline.py`) accepts without flag
overrides:

- `.pdf` — PDF, including browser Print-to-PDF.
- `.png`, `.jpg`, `.jpeg`, `.tif`, `.tiff` — raster screenshots.
- `.txt`, `.md`, `.html`, `.htm` — textual captures (saved HTML
  via browser "Save As Webpage, HTML Only" is one acceptable
  capture form).
- `.json`, `.yaml`, `.yml` — structured data a reviewer obtained
  from a source API or export.

Other extensions (`.docx`, `.pptx`, raw video, archives) are
**rejected** by the pipeline. If a reviewer has evidence in such
a format, they must convert it to a supported type (PDF export
is the simplest route) before storing it here.

## 4. Reviewer-authored capture notes (optional but recommended)

For each evidence file, the reviewer may create a sibling notes
file following this template:

```
reviews/evidence/<filename>.notes.yaml
```

Template contents (replace angle-bracketed values; leave fields
`null` or omit them if the reviewer cannot verify them):

```yaml
# Capture notes for reviews/evidence/<filename>
# These notes are the reviewer's own documentation of capture
# context. They are NOT the intake pipeline's manifest (which is
# generated by `python -m nlp_semantic.intake.cli ingest` into
# hybrid_dataset/intake/manifests/<intk_id>.yaml). They complement
# the intake manifest with capture-time context the pipeline does
# not record.
#
# Reviewer pseudonym convention: `labeler_<NNN>` (see
# hybrid_dataset/dataset/ANNOTATION_GUIDELINES.md §Pseudonym
# convention). Do NOT use real names or emails here.

original_filename: "<the file name as saved on disk>"
capture_date_utc: "<YYYY-MM-DDTHH:MM:SS+00:00 (ISO 8601, timezone-aware)>"
reviewer: "labeler_<NNN>"            # pseudonym; never an email

source_url: "<the exact URL in the browser at capture time, or null>"
source_url_verified_at_capture: true | false
source_identifier: "<e.g. 'PIB PRID 2085000', or null>"
intended_source_id: "<src_<32-hex> that this evidence relates to, or null>"
intended_batch: "<batch_01_sih2024 | ..., or null>"

capture_method: "browser_screenshot" | "print_to_pdf" | "save_as_html" | "api_export" | "other"
browser: "<e.g. Firefox 141, or null>"
operating_system: "<e.g. Windows 11, or null>"

reviewer_notes: >
  Two or three sentences in the reviewer's own words: what the
  evidence shows, what it does NOT show, and any caveats the next
  reviewer or the intake pipeline should know about.

# Do NOT attempt to encode source approval, taxonomy promotion,
# or annotation verification in this file. Those are separate
# workflows:
#   - Source approval: SOURCE_REGISTRATION_GUIDE.md + Chunk 7.2
#     two-reviewer sign-off.
#   - Taxonomy promotion: TAXONOMY_APPROVAL_CHECKLIST.md.
#   - Annotation verification: ANNOTATION_GUIDELINES.md per-record
#     review workflow.
```

Notes files are plain YAML; the intake pipeline does NOT read
them automatically — they are reviewer-facing documentation, not
pipeline input. A notes file left blank or omitted is permissible;
Chunk 7.41 does not enforce their presence.

### 4.1 Why notes are separate from intake manifests

The Chunk 7.39 intake pipeline records: `intake_id`,
`original_filename`, `file_type`, `relative_path`, `sha256`,
`size_bytes`, `intake_timestamp`, optional `source_id`, optional
`achievement_candidate_ids`, optional `proposer`, `status`, and
`validation_findings`. It does **not** record the capture URL,
browser identity, verification-at-capture flag, or free-text
reviewer rationale. The reviewer notes file holds those
capture-time facts.

### 4.2 Linking a notes file to the intake manifest

After running `nlp_semantic.intake.cli ingest <path>`, the
pipeline prints the allocated `intake_id` (format
`intk_<32-hex>`). The reviewer may optionally append that
`intake_id` to the end of the notes file:

```yaml
intake_id_after_ingest: "intk_<32-hex>"
```

This is a one-way reviewer-maintained link; the pipeline manifest
does not point back to the notes file.

## 5. Git tracking and privacy policy

### 5.1 Decision applied in this chunk

Reviewer evidence under `reviews/evidence/` is **gitignored by
default**. Only the structural `.gitkeep` marker is committed. The
pattern mirrors the existing `hybrid_dataset/raw/*` policy
(`.gitignore` and `hybrid_dataset/README.md` §Data safety rules).

Specifically, this chunk adds two lines to the top-level
`.gitignore`:

```
reviews/evidence/*
!reviews/evidence/.gitkeep
```

Reviewer-authored notes files (`*.notes.yaml`) are *also*
gitignored by this pattern. If the owner decides a specific notes
file is safe to commit (contains no PII), the reviewer can
override on a per-file basis with:

```
git add -f reviews/evidence/<filename>.notes.yaml
```

### 5.2 Why this policy

Three reasons derived from the existing project rules:

1. **PII in raw evidence.** `hybrid_dataset/README.md` §Data safety
   rules says: "No private student information in Git. Names,
   roll numbers, emails, phone numbers, scanned IDs, and document
   images must stay in `raw/` locally (or in a secure external
   store), never committed." The same reasoning applies to
   reviewer-captured screenshots: a browser screenshot may
   incidentally include the reviewer's bookmark bar, taskbar,
   open tabs, or window-chrome metadata that identifies them.
2. **Repository size.** Screenshots and PDFs are binary and can
   grow fast. `.gitignore` already excludes model checkpoints,
   embeddings, and raw datasets for this reason.
3. **Reviewer identity.** The project forbids storing a mapping
   from pseudonym to real identity in this repository
   (ANNOTATION_GUIDELINES.md §Pseudonym convention). A
   screenshot can leak identity details that a pseudonym
   deliberately hides.

### 5.3 What this does NOT decide

- **Whether `reviews/evidence/<file>.notes.yaml` files should be
  tracked once the reviewer confirms they are PII-free.** The
  default here is "ignored, allow per-file override with
  `git add -f`." A future chunk may invert this to "tracked by
  default, with a review step" if the owner prefers; this is left
  as an owner decision.
- **Whether a reviewer evidence hash should be committed to a
  tracked index** (e.g. `reviews/EVIDENCE_INDEX.yaml`). The
  intake pipeline already produces manifests under
  `hybrid_dataset/intake/manifests/` that carry the hash and
  provenance; a second tracked index would duplicate that record.
  Not implemented in this chunk.
- **Whether redacted versions of a screenshot (e.g. with the
  reviewer's bookmark bar cropped) should be committed.** The
  current policy permits per-file override; a reviewer who
  prepares a redacted PNG can commit it with `git add -f`.

The three items above are the "Remaining owner decisions" listed
in the Chunk 7.41 report §15.

## 6. Reviewer capture workflow (manual, step-by-step)

Example target: the Chunk 7.3-A.4 PIB SIH 2024 Winners'-List
page. **Chunk 7.41 did not perform these steps** — this section
documents the workflow for a human reviewer to execute later.

### Step 1 — Verify the intended source

In your own browser, open the exact URL recorded in
`hybrid_dataset/metadata/sources.yaml` for the source you intend
to capture:

```
https://www.pib.gov.in/PressReleasePage.aspx?PRID=2085000&lang=2&reg=48
```

Confirm the page content matches the source's `source_name`
field and the `mapping_notes` already in `sources.yaml`.

### Step 2 — Capture

Use the browser's built-in screenshot or Print-to-PDF
functionality. Preserve the full page, not just the viewport.
For long pages, prefer PDF export (`.pdf`) over image stitching.

Do **not** capture the browser chrome if it reveals your
identity (bookmark bar, extensions, email in address bar for
authenticated sites).

### Step 3 — Save to `reviews/evidence/`

Save the captured file as:

```
reviews/evidence/<descriptive_name>.<extension>
```

Example:

```
reviews/evidence/pib_prid_2085000_sih2024_winners_list.pdf
```

Choose a descriptive filename. The pipeline will preserve this
original name in the `original_filename` field of the manifest,
even though the on-disk copy under
`hybrid_dataset/raw/evidence_intake/intk_<hex>/` uses the same
name.

### Step 4 — Write capture notes

Create the sibling notes file following §4 template:

```
reviews/evidence/pib_prid_2085000_sih2024_winners_list.pdf.notes.yaml
```

Fill in the fields you can verify. Leave `null` or omit any
field you cannot verify at capture time.

### Step 5 — Compute SHA-256 (sanity check, pre-ingest)

Optional but recommended, so you can confirm the pipeline reads
the same file:

- **Windows PowerShell:**
  `Get-FileHash reviews\evidence\pib_prid_2085000_sih2024_winners_list.pdf -Algorithm SHA256`
- **Git Bash / Linux / macOS:**
  `sha256sum reviews/evidence/pib_prid_2085000_sih2024_winners_list.pdf`

### Step 6 — Run the intake CLI

From the project root, with the venv active:

```powershell
$env:PYTHONPATH = "src"
python -m nlp_semantic.intake.cli ingest `
  reviews/evidence/pib_prid_2085000_sih2024_winners_list.pdf `
  --evidence-root hybrid_dataset/raw/evidence_intake `
  --manifest-dir hybrid_dataset/intake/manifests `
  --source-id src_5a8a2998d6f44055a42dcfd8991e4d12 `
  --proposer labeler_<your-pseudonym>
```

The pipeline will:

- Compute the SHA-256 (confirm it matches step 5).
- Allocate `intk_<32-hex>` and copy the bytes to
  `hybrid_dataset/raw/evidence_intake/intk_<hex>/pib_prid_2085000_sih2024_winners_list.pdf`.
- Write `hybrid_dataset/intake/manifests/intk_<hex>.yaml` with
  `status: received` and findings including the unconditional
  `AUTHENTICATION_NOT_ESTABLISHED` limitation.
- Flag any duplicate content (if the same bytes have been
  ingested before).

### Step 7 — Validate

```powershell
python -m nlp_semantic.intake.cli validate `
  hybrid_dataset/intake/manifests/intk_<hex>.yaml `
  --evidence-root hybrid_dataset/raw/evidence_intake `
  --sources-yaml hybrid_dataset/metadata/sources.yaml
```

Expected result: `review-evidence: ok | ...` on the stderr summary
line, exit 0. The `source_id` cross-reference check will succeed
because `src_5a8a2998…` is registered.

### Step 8 — Record the intake_id in the notes file (optional)

Append:

```yaml
intake_id_after_ingest: "intk_<32-hex>"
```

to `reviews/evidence/pib_prid_2085000_sih2024_winners_list.pdf.notes.yaml`.

### Step 9 — Preserve the original

Leave the file at `reviews/evidence/<filename>` after ingest. The
intake pipeline made a *copy* under
`hybrid_dataset/raw/evidence_intake/`; it did NOT move the
original. Deleting the original defeats the "reviewer can inspect
original evidence" guarantee.

## 7. What the Chunk 7.39 intake pipeline does NOT change

Running `ingest` on a file in `reviews/evidence/` does not:

- Approve or verify the source. `src_5a8a2998…` remains
  `review_status: unreviewed`, `license: UNKNOWN`.
- Promote any taxonomy label. All 14 primary + 10 domain labels
  remain `status: draft`.
- Verify any annotation. The seven SIH records remain at
  `annotation_status.primary_type: draft`,
  `annotation_status.domain_tags: not_started`.
- Create any `Achievement` or `Annotation` row.
- Change `training_ready_subset` output. Readiness remains
  `any_task=not_ready | all_tasks=not_ready`.
- Authenticate the reviewer. The `AUTHENTICATION_NOT_ESTABLISHED`
  finding is unconditional per Chunk 7.38B / Chunk 7.39 design.
